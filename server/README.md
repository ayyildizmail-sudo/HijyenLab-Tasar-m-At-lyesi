# Shared towel fragrance preference service

The published Site uses its Sites-managed D1 binding `DB`; no external database credentials or analytics provider. This feature belongs only to the separate Tasarım Atölyesi application, not the HijyenLab record system.

`GET /api/fragrance-preferences?productFamily=towels` returns only `{productFamily,seedVersion,source,percentages}`. `POST /api/fragrance-preferences` accepts exactly `{productFamily:"towels",anonymousId:<random UUIDv4>,fragrance:<enum>,revision:<positive safe integer>}`. Valid fragrances: `flambau`, `green_tea`, `bodrum_mandarin`, `lemon`. Roll and folded towels share this population. Wet wipes and unspecified families are rejected; no wet-wipe distribution is invented.

The immutable `500-v1` synthetic starting distribution is 315/95/55/35. These are constants added to aggregate actual preferences, not inserted database rows and not a claim of 500 observed customers. The public API exposes percentages only. The table contains only family, random browser ID, current choice, and monotonic integer revision: no name, telephone, image, timestamp, IP, or application request logs. Hosting infrastructure may retain operational logs outside this application's control. An anonymous browser ID is not identity or a guarantee of one vote per human; clearing browser data/using another device can create another ID.

A primary key on family plus ID and atomic D1 batch upsert+aggregate with a strictly-increasing revision guard prevents late older writes from overwriting newer confirmed choices and makes retries idempotent and preference changes replace the previous choice. GET never writes. An unavailable database returns503; the application must not present fallback percentages as saved/live. Writes require exact same origin, JSON, at most256 bytes, and known fields/enums. There is no endpoint to read individual preferences.

Schema changes are generated with `npm run db:generate`, reviewed, and committed under `drizzle/`. No runtime DDL or seed insertion is allowed. Sites applies migrations during supported publication. Do not replay applied migrations, edit historical migrations, or reset the database on redeployment.

Canonical frontend source is tracked in `frontend/`, including all original assets and behaviors. `scripts/prepare-legacy-frontend.mjs` copies it into ignored `public/` before build/development, excluding Node-only package metadata. `dist/` is generated deployment output only. Existing tests and the asset-versioning helper reference `frontend/`. The maintained Vinext/Sites build plugins remain unchanged. Use the documented Sites build helper. Before publishing, run `npm run test:server`, all frontend regression tests, build, and confirm frontend source hashes remain unchanged. The frontend stays the original HTML/CSS/JS, not a React rewrite.

## Disabled-by-default private lead panel (unpublished development)

`/admin` uses the unmodified Sites starter `app/chatgpt-auth.ts` helper. Sites Dispatch supplies verified Site-scoped identity headers; never expose the Worker directly around Dispatch. Anonymous page visits are sent through Sites sign-in; authenticated non-owners see only their own escaped subject/email and no customer data. Every `/api/admin/*` handler independently authorizes `identity.userId` against `ADMIN_USER_IDS` (JSON string array). Missing, malformed or empty allowlist denies everyone. Email, first login and public profile UUIDs never establish ownership. Static JS/CSS are public and contain no records. Admin HTML/API responses are private/no-store; customer records are fetched only after authorization. Hosted auth/header-spoofing QA must pass before activation; local header fixtures are not proof of hosted identity.

`GET /api/lead-capabilities` is public. Collection remains disabled unless owner IDs, the respective exact `'true'` flag (`LEAD_COLLECTION_ENABLED` / `ANALYTICS_ENABLED`) and explicit integer retention (`LEAD_RETENTION_DAYS` 1–365 / `ANALYTICS_RETENTION_DAYS` 1–90) are all configured. There are no default retention choices and no runtime configuration has been performed. These maximum bounds are implementation limits, not a selected policy. An allowlist entry alone does not activate collection. No first-user ownership grants exist.

`POST /api/leads` accepts explicitly consented `complete` or `contact_request` payloads, metadata only, with immutable UUIDv4 request IDs and SHA-256 canonical-payload replay checks. Complete requests enforce the product quantity floor (BM12 5200, other current products 5000); visual background metadata is not a commercial ground attestation, and the browser quote flow separately enforces its colored-ground minimum; partial unknown product/quantity/fragrance/design are null, never invented zero. Contact name/phone are required. No image bytes, R2 upload, full rendering, payment, order or email is submitted. Browser metadata is untrusted customer input, not a verified production proof. Same-origin JSON, byte/schema bounds, enums, prepared statements, and per-phone/global rate bounds apply. D1 failures never return acceptance. Public GET lead listing does not exist.

`POST /api/analytics` accepts only explicit separate consent, random UUID session/event, enumerated stage and optional enumerated product. No name, email, phone, IP, image, fingerprint or free-text analytics field exists. Deduplication is per UTC day/session/stage/product. Admin totals are distinct session reach, not people or ordered funnels. WhatsApp/phone clicks are not delivery, messages or completed calls. Public capability flags do not expose counts.

`GET /api/admin/leads` supports bounded limit/offset/status; `PATCH /api/admin/leads/:id/status` uses `{status,revision}`, atomic compare-and-swap and actor audit. Valid statuses: new/contacted/quote_sent/closed. Status updates never send communications. `GET /api/admin/stats?days=30` returns aggregate session counts only. Expired rows are never listed; authenticated admin reads purge expired requests, audit and analytics. **A reliable scheduled purge policy remains an activation blocker:** on-read cleanup alone does not guarantee deletion when the app is idle. No scheduler or endpoint has been authorized/configured. Before enabling collection, choose retention, configure and validate periodic cleanup through the supported Sites workflow, disclose the selected policy in consent copy, verify owner/non-owner/anonymous hosted access, and obtain authorization for runtime settings and publication.

Migrations 0001/0002 append separate lead/audit/analytics tables and indexes only, preserving the original fragrance table/migration. `npm run test:server` applies them only to in-memory fixture SQLite, not production. Do not apply/reset production D1 during development.

Email is intentionally disconnected (`emailEnabled:false`), as are images. ### Explicit printed / unprinted request metadata

Every new lead payload requires `printMode: "printed" | "unprinted"`; missing artwork never implies unprinted. Printed complete requests retain the product floors and design metadata. Unprinted requires `design:null`, so no artwork/color/QR metadata is accidentally carried across modes. For known quantity, known product is required and quantity must be at least one exact carton multiple: BM12 400, BM15 500, BM545 625, BM21 1,000 (existing maximum 1,000,000 retained). Complete requests still require company/contact name/phone and explicit consent. Unprinted towel SKUs require `fragrance:"flambau"`; BM21 wet wipes require `fragrance:"green_tea"`. Partial requests may retain null unknown fragrance but cannot claim another fixed fragrance. Printed BM21 requires at least 10,000 units and offers the same four confirmed fragrance choices, locally only: no towel preference percentages or preference-service calls are used. No backend fragrance-preference vote is generated for unprinted products. BM21 is an enabled app SKU; these validation changes do not activate lead intake, analytics or email services.

The approved same-white unit price and shipping (Bodrum 0, elsewhere 200 TL/carton) remain the frontend commercial calculator's responsibility; no submitted price/klişe value is accepted or treated as a binding quote. Admin records expose the explicit print mode. Migration 0003 rebuilds the lead table locally to adjust its complete-design constraint, explicitly backfills historical records as printed, and preserves audit rows through a staging copy; it does not rely on disabling foreign keys. In-memory transactional tests preserve historical leads, audits and fragrance rows and verify foreign keys. No production migration has been applied.
