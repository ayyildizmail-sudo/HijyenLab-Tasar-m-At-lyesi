# Shared towel fragrance preference service

The published Site uses its Sites-managed D1 binding `DB`; no external database credentials or analytics provider. This feature belongs only to the separate Tasarım Atölyesi application, not the HijyenLab record system.

`GET /api/fragrance-preferences?productFamily=towels` returns only `{productFamily,seedVersion,source,percentages}`. `POST /api/fragrance-preferences` accepts exactly `{productFamily:"towels",anonymousId:<random UUIDv4>,fragrance:<enum>,revision:<positive safe integer>}`. Valid fragrances: `flambau`, `green_tea`, `bodrum_mandarin`, `lemon`. Roll and folded towels share this population. Wet wipes and unspecified families are rejected; no wet-wipe distribution is invented.

The immutable `500-v1` synthetic starting distribution is 315/95/55/35. These are constants added to aggregate actual preferences, not inserted database rows and not a claim of 500 observed customers. The public API exposes percentages only. The table contains only family, random browser ID, current choice, and monotonic integer revision: no name, telephone, image, timestamp, IP, or application request logs. Hosting infrastructure may retain operational logs outside this application's control. An anonymous browser ID is not identity or a guarantee of one vote per human; clearing browser data/using another device can create another ID.

A primary key on family plus ID and atomic D1 batch upsert+aggregate with a strictly-increasing revision guard prevents late older writes from overwriting newer confirmed choices and makes retries idempotent and preference changes replace the previous choice. GET never writes. An unavailable database returns503; the application must not present fallback percentages as saved/live. Writes require exact same origin, JSON, at most256 bytes, and known fields/enums. There is no endpoint to read individual preferences.

Schema changes are generated with `npm run db:generate`, reviewed, and committed under `drizzle/`. No runtime DDL or seed insertion is allowed. Sites applies migrations during supported publication. Do not replay applied migrations, edit historical migrations, or reset the database on redeployment.

Canonical frontend source is tracked in `frontend/`, including all original assets and behaviors. `scripts/prepare-legacy-frontend.mjs` copies it into ignored `public/` before build/development, excluding Node-only package metadata. `dist/` is generated deployment output only. Existing tests and the asset-versioning helper reference `frontend/`. The maintained Vinext/Sites build plugins remain unchanged. Use the documented Sites build helper. Before publishing, run `npm run test:server`, all frontend regression tests, build, and confirm frontend source hashes remain unchanged. The frontend stays the original HTML/CSS/JS, not a React rewrite.
